# Observabilidad Industrial

MLOps Pillar #5: Detectando el
Fallo Silencioso

### Definición de la Fase

Es el proceso de vigilancia continua de los sistemas de ML en producción. No solo monitoreamos
la **salud de la infraestructura** (latencia, CPU), sino la **integridad
estadística** del modelo. El objetivo es identificar cuándo el conocimiento del
modelo se vuelve obsoleto antes de que afecte financieramente al negocio.

#### Concepto: El Fallo Silencioso

"Un servidor caído devuelve un error 500. Un modelo degradado devuelve un '200 OK' con una
predicción que hace perder dinero. El monitoreo proactivo es la única cura para la degradación
estadística."

## Conceptos Pilares

- **Data Drift:** Cambio en la distribución de las variables
  de entrada ($P(X)$). Los datos de hoy ya no se parecen a los de entrenamiento.
- **Concept Drift / Model Decay:** Cambio en la relación entre
  entrada y salida ($P(Y|X)$). El modelo pierde precisión incluso si los datos parecen iguales.
- **Métricas SRE:** Vigilancia técnica de latencia (P99), uso
  de memoria GPU/RAM y tasa de errores de API.

## Análisis de Valor

#### Ventajas

- • Prevención de pérdidas financieras por predicciones erróneas.
- • Activación de ciclos de entrenamiento continuo (CT).
- • Mayor confianza de los stakeholders en la IA.

#### Desventajas / Retos

- • Retraso en la obtención de "Ground Truth" (etiquetas reales).
- • Costo de almacenamiento de logs de inferencia masivos.
- • Complejidad en la definición de umbrales de alerta (Alert Fatigue).

### El "Fallo Silencioso"

A diferencia de una caída de servidor, un modelo puede seguir respondiendo 200 OK mientras
sus predicciones son basura.

#### Data Drift

Los datos que entran hoy son distintos a los de
ayer.

#### Model Decay

El rendimiento baja naturalmente con el tiempo.

#### Trigger de Re-entrenamiento

La observabilidad es el motor del **Entrenamiento Continuo (CT)**. Cuando el
monitoreo detecta una caída significativa en el rendimiento, dispara automáticamente el
pipeline de entrenamiento para actualizar el modelo.

"No puedes mejorar lo que no puedes
medir."

## Etapas del Ciclo de Observabilidad

1. Detección de Data Drift

### Validación Estadística de Distribución

Comparamos la distribución de entrenamiento contra la de
producción usando tests como Kolmogorov-Smirnov.

from scipy.stats import ks\_2samp
def check\_data\_drift(train\_series,
prod\_series, threshold=0.05):
# Test KS: ¿Pertenecen ambas muestras a la misma distribución?
statistic, p\_value = ks\_2samp(train\_series, prod\_series)
if p\_value < threshold: print("ALERTA: Drift detectado en la característica")
return True
return False

## Foco: Validación Cruzada (Baseline de Alerta)

### El Ancla Estadística

En el monitoreo, la **Validación Cruzada** no es solo para entrenar. Se
utiliza para establecer la **varianza normal** de las métricas. Si en
entrenamiento el F1 varió entre 0.82 y 0.85 entre folds, una caída a 0.80 en producción
es una anomalía real, no ruido estadístico.

Uso Práctico: Define los umbrales de alerta
basados en la desviación estándar obtenida en el Cross-Validation de la fase de
desarrollo.

### Conceptos de Valor

#### Ventajas en Alerta

Evita la fatiga de alertas al ignorar
variaciones que el modelo ya mostró durante el entrenamiento (robusta vs
outliers).

#### Desventajas

Requiere guardar la metadata de todos los
folds del entrenamiento histórico para comparación en vivo.

## Higiene de la Observabilidad

#### Error: Alert Fatigue

Configurar alertas en cada fluctuación mínima del Data Drift. **Consecuencia:** El
equipo de Ops ignora los correos y el sistema falla realmente. **Solución:** Usar
umbrales basados en percentiles históricos.

#### Práctica: Feedback Loop Cerrado

No solo alertar; el monitoreo debe disparar automáticamente un **Shadow
Deployment** de un modelo nuevo para validar si el re-entrenamiento corrige el drift.
