# CI/CD en MLOps

## MLOps Pillar #3: El Puente a Producción

### Definición

Es la automatización del ciclo de vida del ML. A diferencia del software tradicional, aquí
integramos no solo **código**, sino también **datos** y
**modelos**. El objetivo es que cualquier cambio en la lógica o en la distribución
de datos dispare automáticamente un flujo de pruebas y despliegue confiable.

#### Elemento Distintivo: CT

"En DevOps el despliegue es el fin. En MLOps, el despliegue es el inicio del
**Entrenamiento Continuo (CT)**: el sistema debe ser capaz de re-entrenarse solo
cuando el mundo real cambia."

## Conceptos Pilares

- **CI (Integración Continua):** Pruebas unitarias de scripts
  y validación de la integridad de los nuevos datos de entrenamiento.
- **CD (Entrega Continua):** Despliegue automático de
  servicios de inferencia (APIs) en entornos de Staging/Prod.
- **Model Registry:** Inventario centralizado donde los
  modelos aprobados se etiquetan y se versionan semánticamente.

## Análisis de Valor

#### Ventajas

- • Cero tiempo de inactividad en actualizaciones.
- • Mitigación de "Training-Serving Skew".
- • Auditoría total de quién puso qué modelo en producción.

#### Desventajas

- • Alta complejidad en orquestación de clústeres.
- • Costo de infraestructura para pipelines paralelos.
- • Riesgo de automatizar el despliegue de sesgos.

2. Validación de Modelos

### Gateway de Calidad Predictiva

El modelo solo se registra si supera al modelo actual en
producción (Champion vs Challenger).

# check\_model\_performance.py
def validate\_model(new\_f1, current\_f1,
threshold=0.01):
# Solo permitimos el despliegue si el modelo es al menos 1% mejor
if new\_f1 > (current\_f1 + threshold):
print("Model Approved for Production")
return True
return False

## Foco: Validación Cruzada (K-Fold)

### Definición y Concepto

La Validación Cruzada divide el dataset en **$K$ particiones**. Entrena $K$
veces, usando cada vez un grupo distinto para validar y el resto para entrenar,
promediando los resultados finales.

Uso en CI: Se utiliza en el pipeline para
asegurar que el performance del modelo no depende de un split aleatorio afortunado.

### Análisis Crítico

#### Ventajas

Estimación de error más realista. Aprovecha
todos los datos para validar. Reduce el sesgo de selección.

#### Desventajas

Coste computacional $K$ veces mayor. No apto
para series de tiempo (requiere TimeSeriesSplit).

## Higiene del Pipeline CI/CD

#### Error: Docker Bloat

Incluir el dataset de entrenamiento dentro de la imagen Docker. **Impacto:**
Imágenes de 10GB que tardan minutos en desplegar. **Solución:** Los datos se
consumen vía API o montaje de volúmenes; la imagen solo lleva código y pesos.

#### Práctica: Smoke Tests de Inferencia

Antes de desplegar, enviar 5 peticiones reales al contenedor en Staging. Si el modelo no
responde en < 100ms, el despliegue se cancela (Rollback).

##### Versiones Inmutables

¿Cada modelo en el Registry tiene un hash único vinculado al commit

##### Métrica de Negocio en CI

¿El pipeline valida KPIs de negocio (ej. margen de ganancia esperado)
antes de aprobar?

##### Data Schema Validation

¿Se ejecuta un test de calidad de datos antes de iniciar el
re-entrenamiento (CT)?

##### Estrategia de Despliegue

¿Se ha definido el uso de Canary o Blue/Green para evitar impacto en
usuarios reales?

##### Rollback Automático

¿El orquestador es capaz de volver a la versión anterior si el
monitoreo detecta anomalías?
